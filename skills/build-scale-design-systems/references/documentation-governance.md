# Documentation and governance

## Documentation page

Include status, owner/support, purpose, when to use, when not to use, real product examples, anatomy, behavior, content, accessibility, variants/states, tokens/API, composition, responsive/platform/localization behavior, examples and non-examples, test guidance, version, changelog, migration, and related patterns.

Lead with real tasks and outcomes so adopters can recognize relevance before reading implementation details.

## Contribution paths

- feedback or issue;
- product-specific extension reported to system team;
- documented candidate;
- small fix or documentation contribution;
- new/changed shared asset through cross-disciplinary review.

For each path define template, triage owner, expected response, evidence, review disciplines, decision, credit, release, and support. Contribution must not mean transferring all labor to product teams.

## Decision rights

State who recommends, reviews, decides, implements, releases, supports, and can approve exceptions. A curator model integrates contributions; a producer model builds more centrally. Use a hybrid when capacity and ownership demand it.

## Quality gates

Check product evidence, API/design quality, content, accessibility, localization, platform behavior, tests, security/privacy where relevant, documentation, versioning, and migration. Gates should be proportional; a typo fix should not require the same process as a breaking component.

## Release and deprecation

Use semantic or explicit version policy, release notes, upgrade guidance, codemods or migration help where feasible, deprecation warnings, support window, usage telemetry, and removal criteria. Never silently change semantics under an existing API.

## Governance tone

Use partnership, transparent rationale, fast support, and incentives. Exceptions are evidence: record why they exist and whether the shared pattern should change.
