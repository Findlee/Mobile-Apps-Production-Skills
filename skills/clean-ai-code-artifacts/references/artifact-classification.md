# Artifact Classification

Use this guide to classify observable code artifacts. Do not infer authorship from prose style, naming, complexity, or commit history alone.

## Remove

Remove when the text or code has no product, maintenance, legal, or tooling purpose:

- assistant-facing prose copied into source code, such as "Here is the implementation";
- explicit conversational markers such as "As an AI" or "generated by ChatGPT" when no disclosure or provenance rule requires them;
- tutorial narration that only restates the next line of code;
- temporary debug prints, copied sample payloads, or demonstration branches left by the completed task;
- abandoned placeholders whose intended behavior is already implemented elsewhere;
- unused imports, helpers, fixtures, or mock data introduced by the current change;
- duplicate comments repeated across nearby code without adding context.

## Rewrite

Rewrite instead of deleting when the underlying information remains useful:

| Candidate | Rewrite toward |
|---|---|
| "We use this helper to make things easier" | The concrete invariant or constraint the helper protects |
| Long tutorial explaining syntax | A concise reason the non-obvious construct is required |
| Vague `TODO` | A scoped task, decision owner, issue reference, or explicit removal |
| Defensive branch labeled "just in case" | The failure condition and expected recovery behavior |
| Repeated implementation comment | A clearer name, extracted concept, or single authoritative note |

## Preserve

Preserve when the artifact serves a real contract:

- copyright, license, attribution, or third-party notices;
- generated-file headers, generator versions, source mappings, schema metadata, and `DO NOT EDIT` warnings;
- lint, formatter, type-checker, compiler, test, coverage, or documentation directives;
- public API documentation and externally consumed examples;
- comments explaining security, privacy, concurrency, data integrity, compatibility, migration, or performance constraints;
- issue links, architecture decisions, incident references, and temporary compatibility notes with a real owner or removal condition;
- user-visible disclosure required by policy, contract, or organizational rules.

## Investigate

Investigate before changing:

- unfamiliar annotations or magic comments;
- notices in vendored, generated, migrated, or copied code;
- comments referenced by tests, documentation tooling, release scripts, or code generators;
- placeholders in partially completed work outside the current task;
- attribution whose legal status is unclear;
- apparently redundant compatibility branches without platform coverage evidence.

## Decision test

For each candidate ask:

1. What observable purpose does this serve?
2. What would fail, become misleading, or become harder to maintain if it disappeared?
3. Is its ownership established by code generation, licensing, policy, or repository convention?
4. Can naming or structure preserve the useful meaning more clearly?
5. Can the change be verified without guessing?

If the answers remain unclear, preserve the artifact and report the uncertainty.
