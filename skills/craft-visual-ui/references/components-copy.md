# Components and interface copy

Use this reference to make component role, state, and language clear.

## Action hierarchy

- Give the most important next action primary emphasis when the flow has a clear primary action.
- Keep secondary actions visible but quieter; use tertiary treatment for low-priority actions.
- Avoid several equally prominent actions in one decision area.
- Place actions near the content or object they affect.
- Separate destructive actions from common actions and scale friction to consequences.
- Make all interactive treatments recognizable without color alone.

## Buttons and links

- Label controls with the action and, when useful, its object: “Save draft,” “Send invite,” or “Delete account.”
- Avoid vague labels when the surrounding context does not make the destination obvious.
- Ensure the entire intended target is interactive and sized for the current platform and input method.
- Balance icon and text visually; do not use an unfamiliar icon without a label or accessible name.
- Preserve visible focus, pressed, selected, loading, success, and error feedback.
- Avoid disabling an action without explaining what is required; when feasible, allow activation and reveal a clear correction path.

## Forms

- Use persistent visible labels and keep help or errors attached to their fields.
- Ask for the minimum information needed at the current stage.
- Choose controls based on choice count, comparison needs, expected input, and platform conventions.
- Match field width and keyboard/input mode to expected content when practical.
- Group related fields and use a single-column flow when it improves completion and scanning.
- Preserve user input after validation or submission errors.
- Mark required or optional fields consistently according to the form's balance; do not make users decode mixed conventions.

## Component states

Specify at least the states that can occur: default, hover where applicable, focused, pressed, selected, loading, disabled, error, and success. Different states need more than a subtle color shift when the distinction is important.

Use status styling consistently, but keep error and danger from visually overwhelming normal use. A destructive action need not be a dominant red button before the user chooses it.

## Interface copy

- Be concise, direct, and specific.
- Front-load distinguishing words for scanning.
- Use familiar vocabulary and keep one term for one object or action.
- Prefer plain language over internal, technical, clever, or marketing-induced names.
- Write headings and link text that remain meaningful out of surrounding prose.
- Use numerals where they improve rapid scanning, while respecting locale and content conventions.
- Remove text that repeats what layout and controls already communicate.

## Errors and confirmations

- State what happened, why when known, and what the user can do next.
- Avoid blame, codes without explanation, and false certainty.
- Name the affected object or field.
- Confirm meaningful completion and show the resulting state or next step.
- Keep success messages proportional; do not interrupt the user for routine confirmations that are already visible.
