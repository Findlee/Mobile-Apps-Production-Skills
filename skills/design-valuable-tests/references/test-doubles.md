# Test Doubles

## Vocabulary

- **Dummy:** fills a parameter but is not used.
- **Stub:** returns controlled input to the system under test.
- **Fake:** working simplified implementation with meaningful behavior.
- **Spy:** records an observable interaction for later verification.
- **Mock:** preprogrammed interaction expectation, often generated by a framework.

Do not verify interactions with stubs; they provide inputs, not externally meaningful outputs.

## Classify the dependency

### In-process collaborator

Prefer the real collaborator when it participates in domain behavior. Mocking it couples tests to internal choreography.

### Managed out-of-process dependency

The application owns and can reset it, such as its database. Prefer a real instance in integration tests when semantics matter. A fake/in-memory replacement is safe only if its behavior is sufficiently equivalent for the risk.

### Unmanaged out-of-process dependency

Another system observes it, such as a message bus, payment gateway, email provider, or partner API. Verify the system-edge contract through a mock/spy, local emulator, sandbox, or contract test as appropriate.

## Use mocks well

- Verify meaningful commands or published events at the system edge.
- Assert payload and semantic intent, not incidental call sequence, unless order is the contract.
- Mock types/contracts owned by the application when practical.
- Avoid one-mock-per-test rules; use only the doubles the scenario requires.
- Keep verification at the observable boundary, not between internal layers.

## Interface caution

Do not create an interface solely to mock a domain class. An interface for an external boundary may be justified even with one production implementation because the boundary and interaction are meaningful; state that reason explicitly.
