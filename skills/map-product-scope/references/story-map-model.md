# Story Map Model

## Orientation

Read a map in two directions:

- **Left to right:** the narrative flow or chronology of using the product.
- **Top to bottom:** increasing detail, alternatives, and lower priority within an activity.

Horizontal lines create coherent releases or learning slices across the journey.

## Levels

### Outcome frame

State the actor, problem, desired outcome, current workaround, and evidence. Keep solution language out unless it is a hard constraint.

### Backbone

Use a short sequence of major user activities. It should let a new participant retell the whole story without reading every card.

### Tasks

Describe what users do, not the screens, endpoints, database tables, or teams that implement it.

### Details and variations

Add alternative paths, rules, exceptions, data needs, and implementation notes beneath the relevant task. Label technical enablers rather than letting them replace the user story.

## Text representation

When a physical or visual board is unavailable, use a table:

| Slice / activity | Activity A | Activity B | Activity C |
|---|---|---|---|
| Backbone | ... | ... | ... |
| Learning slice | ... | ... | ... |
| First release | ... | ... | ... |
| Later | ... | ... | ... |

Add a separate list for assumptions and unresolved questions so they do not look like committed scope.

## Quality check

A good map makes the whole experience visible, supports retelling, exposes missing paths, and permits multiple useful horizontal slices. It is not merely a two-dimensional issue tracker.

Conceptual lineage: user story mapping and story conversations.
