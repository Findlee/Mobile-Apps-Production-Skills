# AI Product Review Lens

Reviewed: 2026-08-08

Use this lens for generative AI, copilots, chat assistants, AI search, recommendations generated by foundation models, autonomous agents, tool-using agents, AI content generation, and other model-driven product behavior.

Do not review an AI product only as a model benchmark. Review the full chain:

`Model/component quality -> System behavior -> User task success -> Product outcome -> Business outcome`

## 1. Why AI?

Ask:

- What user job requires probabilistic/generative behavior?
- Would rules, search, templates, or conventional software solve the job more reliably/cheaply?
- What capability makes AI materially better?
- Is AI visible because it creates value or because it is fashionable?

If a simpler deterministic solution meets the outcome, prefer simplicity.

## 2. AI interaction contract

Define:

- user input;
- system/developer context;
- tools/data sources;
- model/provider;
- expected output;
- allowed uncertainty;
- forbidden behaviors;
- correction/retry path;
- fallback/degraded mode;
- user-visible disclosure where needed;
- data retention/privacy behavior;
- latency/cost expectations.

If the product cannot state this contract, product behavior is under-specified.

## 3. Model/system quality dimensions

Choose only dimensions relevant to the task:

- factual correctness;
- groundedness/source fidelity;
- completeness;
- relevance;
- instruction following;
- consistency;
- structured-output validity;
- tone/style;
- language quality;
- safety;
- bias/subgroup performance;
- tool selection;
- tool argument precision;
- action correctness;
- state consistency across turns;
- latency;
- cost;
- availability/fallback.

A generic "quality score" is usually too weak.

## 4. Evals

Follow an eval-driven process:

1. Define the task and success criteria.
2. Build a representative dataset from production/historical/domain cases where possible.
3. Include typical, edge, and adversarial cases.
4. Choose specific graders/metrics.
5. Calibrate automated graders with human judgment.
6. Run multiple trials for nondeterministic agent tasks where needed.
7. Compare model/prompt/tool changes against a baseline.
8. Continuously add production failures to the eval set.

For agents, distinguish:

- transcript/trajectory;
- tool calls;
- final environment outcome.

A transcript saying "done" is not proof the action succeeded.

## 5. Agent architecture

Do not add agentic complexity by default.

Review whether the product truly needs:

- multi-step planning;
- tool autonomy;
- multi-agent routing;
- long-running state;
- autonomous retries;
- memory;
- external actions.

Prefer the simplest architecture that reliably solves the task. Add complexity only when measured outcomes justify it.

## 6. Tool/action safety

For tool-using AI, review:

- permissions;
- least privilege;
- user confirmation for consequential actions;
- idempotency;
- duplicate action protection;
- argument validation;
- tool errors/timeouts;
- partial failure;
- rollback/compensation;
- audit trail;
- sandboxing where appropriate;
- handoff to human or deterministic workflow.

High-risk actions should not depend only on natural-language confidence.

## 7. Confabulation and information integrity

Review whether false/confident content can materially harm the user.

Mitigations may include:

- retrieval/grounding;
- constrained outputs;
- source display;
- uncertainty communication;
- deterministic verification;
- human review;
- refusal/escalation;
- narrower supported scope;
- post-generation validation.

Do not use a generic disclaimer as the only mitigation for a high-consequence task.

## 8. Human-AI configuration

Review risk of:

- over-reliance;
- automation bias;
- inappropriate anthropomorphism;
- emotional dependency/entanglement where relevant;
- users misunderstanding AI capability or authority;
- unclear responsibility for actions.

Design should make system limits and control boundaries understandable.

## 9. Data privacy and provenance

Review:

- what user data enters the model/provider;
- sensitive data minimization;
- retention and deletion;
- training/reuse policy where relevant;
- third-party providers;
- logging/redaction;
- retrieval sources;
- generated content provenance where relevant;
- IP/licensing risk where relevant.

Do not assume provider defaults satisfy the product's privacy obligations.

## 10. Bias and subgroup/language quality

When the product serves diverse users or consequential use cases:

- test relevant languages;
- test important subgroups/scenarios;
- compare failure rates/quality;
- identify training/context gaps;
- avoid assuming one aggregate eval score represents all users.

## 11. Model change management

Treat model/prompt/tool changes as product changes when they can alter behavior.

Review:

- version pinning where possible;
- regression suite;
- canary/limited rollout;
- quality guardrails;
- latency/cost guardrails;
- rollback;
- production monitoring;
- incident log.

## 12. AI product metrics

Separate:

### Model/system metrics
- eval pass rate;
- factuality/grounding;
- tool success;
- refusal correctness;
- latency;
- cost;
- error rate.

### User/task metrics
- successful task completion;
- retries/regenerations;
- abandon rate;
- time-to-success;
- correction rate;
- escalation rate.

### Product outcomes
- activation;
- retention;
- conversion;
- recurring value;
- revenue/LTV where relevant.

A model metric improvement is not automatically a product win.

## 13. NIST GAI risk prompts

Use these as a relevance screen, not a mandatory checklist:

- confabulation;
- dangerous/violent/hateful content where applicable;
- data privacy;
- harmful bias/homogenization;
- human-AI configuration;
- information integrity;
- information security;
- intellectual property;
- abusive content;
- third-party/value-chain integration;
- other domain-specific harms.

Allocate review effort by likelihood x consequence and use-case context.
